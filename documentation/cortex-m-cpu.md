# Cortex-M CPU deployment

The `SSE-320-M85` target runs TinyCNN on the Cortex-M85 CPU of the
Corstone-320 FVP using CMSIS-NN. It has its own application project, board
layer, AI layer and generated model directory. It does not select the
Ethos-U runtime backend, NPU driver or NPU initialization source.

## Build and run

1. Open `cmsis-executorch-simple.csolution.yml` in CMSIS Solution.
2. Select `SSE-320-M85` and the `Debug` build type.
3. Use **Build**. The build exports the CPU model and generates its operator
   selection. If it reports that `cpu.clayer.yml` changed, build again.
4. Use **Run**. Successful numerical validation prints three `Case ...: PASS`
   lines and `Test_result: PASS`. A mismatch prints `Test_result: FAIL`.

The existing `SSE-320-U85` target remains the NPU example. The solution's
legacy `mlops.npu`/Vela metadata describes that example; the CPU project's
export step does not consume that metadata or invoke Vela.

## Export and validation

`model/export_cpu.py` uses the installed ExecuTorch 1.4.1 API. That API
differs from the newer API in the PyTorch blog: it uses `CortexMQuantizer()`,
then `to_edge`, then `CortexMPassManager(...).transform()`.

The model and four-dimensional inputs use channels-last storage with logical
NCHW shapes. This is required by this version's convolution quantizer.
Generated firmware inputs are written in the corresponding physical NHWC order.

The example fixes the random seed to reproduce its untrained TinyCNN weights.
It calibrates with synthetic samples and validates ramp, zero and random
inputs against the host's quantized PyTorch outputs. The acceptance tolerance
is two integer output codes (two output quantization steps).
The FP32 reference and quantization error are recorded separately. These
checks establish deployment correctness; they do not establish trained-model
accuracy or performance.

The current export exposes signed INT8 input and output tensors. It removes
the calibrated input quantize and final output dequantize operations, then
re-exports using INT8 inputs. Host checks require the integer results to match
the original quantized model exactly and verify INT8 input/output types in
the serialized program. Biases and accumulators use wider integer types.

Input bytes must already represent the model's normalized input, quantized
as `clamp(round(normalized_value / input_scale) + input_zero_point, -128, 127)`.
They are not raw unsigned RGB pixels. The calibration-derived scale and zero
point for each boundary are saved in `model/cpu/validation.json` and in the
reference header. Output values represent quantized logits, not probabilities;
for classification, argmax can operate directly on these per-tensor INT8 logits.
Only when real-valued outputs are needed, decode with
`real_output = (int8_output - output_zero_point) * output_scale`.

Export checks require convolution, linear and max-pooling to become Cortex-M
operators and reject delegated graphs. Component generation rejects operators
missing from the runtime pack and omits the Ethos-U backend for the CPU target.

Generated outputs:

- `model/cpu/model.pte`: serialized CPU model.
- `model/cpu/graph.txt`: lowered graph for operator inspection.
- `model/cpu/validation.json`: host references, tolerance and quantization error.
- `ai_layer/cpu_model/model_pte.h`: embedded model bytes.
- `ai_layer/cpu_model/model_reference.h`: three inputs and expected outputs.
- `ai_layer/cpu_model/model_io.h`: INT8 quantization and memory-pool metadata.
- `ai_layer/cpu.clayer.yml`: model-specific CMSIS components.

The runner reserves planned tensor memory plus 64 KiB for method metadata,
and 16 KiB for temporary memory. It checks planned-buffer allocations and prints planned tensor bytes.
These reservations are initial limits, not measured peak RAM. The board still
uses the existing FVP memory map and 96 KiB heap; physical-board memory tuning
and performance measurements remain separate work.

## Dependencies and current validation status

The solution and projects select `PyTorch::ExecuTorch@1.4.1`; Python requirements
select `executorch==1.4.1`, `torch==2.13.0`, and `torchao==0.18.0`.
The existing virtual environment and installed pack match these versions.

CMSIS environment checks passed with Toolbox 2.15.0, CMake 4.2.1,
Ninja 1.13.2, AC6 6.24.0 and GCC 14.3.1. The generated environment passed
consumed-field validation; full JSON Schema validation was unavailable
because the Python `jsonschema` package is absent.

The float-boundary TinyCNN passed all three reference cases on the M85 FVP:
errors were 0, 0 and one output quantization step, with 3,840 planned tensor
bytes. The current INT8-boundary TinyCNN passed host boundary-equivalence,
serialized INT8 input/output and NHWC-storage checks. It produces a
10,872-byte program with 2,944 planned tensor bytes. Firmware headers must be
regenerated by a CPU build before running this changed interface. Its FVP
numerical checks remain pending; the earlier target pass validates the old
float-boundary interface only.

Runtime and AI layers select ExecuTorch 1.4.1 consistently. Component selection
reads every serialized operator table, including layout operators, and checks
each operator against the installed pack. Pack-selection and missing-layout
operator regression checks passed.

## SqueezeNet rock-paper-scissors

The separate `SSE-320-RPS` target exports the supplied trained SqueezeNet 1.1
checkpoint with INT8 input/output and integer RGB preprocessing. See
[RPS export and validation](rps.md) for the local asset configuration,
four-class ordering, memory requirements and build instructions.

## M55 and a trained model

The exporter also accepts `--cpu cortex-m55`. This selects the AOT CPU/ISA
configuration only; the supplied firmware target remains M85. M55 execution
needs a separate Corstone-300 or physical-board target, matching startup,
memory map and simulator/debug configuration. The CPU exporter currently
shares one output directory, so export only for the firmware target being built.

For a real application, load trained weights, replace synthetic calibration
with representative data, update input/output handling and test cases, then
validate accuracy, operator coverage and memory on the selected board.
